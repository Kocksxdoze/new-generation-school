# NGS Backend

API + данные для сайта New Generation School: новости, медиа-библиотека и
динамический контент страниц (для будущей админ-панели).

## Стек

- **Node.js + Express** (обычный JS, ESM-модули)
- **SQLite** через **Prisma ORM**
- **JWT** (httpOnly-cookie) для авторизации админов
- **Multer + Sharp** для загрузки и обработки картинок/SVG
- **Zod** для валидации входных данных

## Структура

```
backend/
├── prisma/
│   ├── schema.prisma       # модель данных
│   ├── seed.js             # создаёт первого админа + страницу "home"
│   └── migrate-legacy.js   # импорт данных из старой Django-базы
├── src/
│   ├── config/              # env, подключение к БД
│   ├── middlewares/         # auth, ошибки, загрузка файлов, валидация
│   ├── modules/
│   │   ├── auth/             # логин, пользователи админки
│   │   ├── news/              # CRUD новостей
│   │   ├── media/             # медиа-библиотека
│   │   └── pages/              # страницы + динамические блоки (sections)
│   ├── routes/index.js       # сборка всех роутов
│   └── app.js                # настройка Express
├── uploads/                  # загруженные файлы (не в git)
└── server.js                 # точка входа
```

Каждый модуль в `modules/` имеет одинаковую форму: `*.routes.js` →
`*.controller.js` → `*.service.js` (+ `*.validation.js`). Роуты не содержат
логики, контроллеры не содержат SQL/Prisma-запросов — это всегда в
сервисах. Это и есть тот единообразный, предсказуемый стиль, который не
даёт коду превращаться в кашу по мере роста проекта.

## Быстрый старт

```bash
cp .env.example .env
# открой .env и заполни JWT_SECRET и SEED_ADMIN_PASSWORD

npm install
npm run prisma:migrate      # создаёт SQLite-файл и таблицы
npm run db:seed             # создаёт первого админа + страницу "home"

npm run dev                 # http://localhost:4000
```

## Перенос данных со старого сайта (Django + SQLite)

1. Положи старый `.sqlite`-файл в `prisma/legacy.sqlite`.
2. Скопируй папку `MEDIA_ROOT` со старого сайта (картинки новостей) в
   `uploads/legacy-media/`, сохранив ту же структуру подпапок
   (`post_images/...`).
3. Запусти:
   ```bash
   npm run db:import-legacy
   ```
   Скрипт идемпотентен — его можно запускать повторно, уже импортированные
   новости и существующие пользователи будут пропущены.

Пароль администратора из старой базы (`users.password`) уже был в формате
bcrypt, так что он переносится как есть — логиниться можно тем же паролем.

## Создание дополнительных админ-пользователей

Публичной регистрации в админку нет специально — только через CLI или уже
залогиненным ADMIN через API:

```bash
npm run admin:create -- --username=jane --email=jane@ngs.uz --password=strongpass123 --role=EDITOR
```

## Основные эндпоинты

### Публичные (использует Next.js-фронтенд)

| Метод | Путь                   | Описание                              |
| ----- | ---------------------- | -------------------------------------- |
| GET   | `/api/news`             | список опубликованных новостей (пагинация, фильтр по категории/поиску) |
| GET   | `/api/news/:slug`       | одна новость                          |
| GET   | `/api/news/categories`  | список категорий                      |
| GET   | `/api/site/:slug`       | страница целиком со всеми блоками (например `/api/site/home`) |

### Auth

| Метод | Путь                     | Описание                       |
| ----- | ------------------------ | -------------------------------- |
| POST  | `/api/auth/login`         | вход (username/email + пароль) |
| POST  | `/api/auth/logout`        | выход                          |
| GET   | `/api/auth/me`            | текущий пользователь           |
| POST  | `/api/auth/change-password` | смена пароля                |
| POST  | `/api/auth/users`         | создать пользователя (только ADMIN) |

### Админка (требуют авторизации)

| Метод | Путь                                | Описание                        |
| ----- | ------------------------------------ | -------------------------------- |
| GET/POST/PUT/DELETE | `/api/admin/news[/:id]`  | полный CRUD новостей (включая черновики) |
| GET/POST            | `/api/admin/media`       | список и загрузка файлов          |
| PATCH/DELETE         | `/api/admin/media/:id`  | изменить alt-текст / удалить файл |
| GET/POST             | `/api/admin/pages[/:slug]` | список страниц, создание страницы |
| POST                  | `/api/admin/pages/:slug/sections` | добавить блок на страницу |
| POST                  | `/api/admin/pages/:slug/sections/reorder` | сохранить новый порядок блоков |
| PATCH/DELETE          | `/api/admin/pages/sections/:id` | изменить/удалить блок |

## Как устроен динамический контент страниц

Каждая страница (`Page`) состоит из упорядоченного списка блоков
(`Section`). У блока есть `type` (какой компонент фронтенда его
рендерит — `hero`, `values`, `testimonials`, ...) и `data` — JSON с
конкретным содержимым (тексты, ссылки на картинки, иконки). Админ может:

- менять `data` любого блока (тексты/картинки) — без деплоя фронтенда;
- скрывать блок (`visible: false`), не удаляя его;
- менять порядок блоков (`/sections/reorder`) — это и есть "адаптивное
  расположение" контента, которое просил заказчик;
- добавлять новый блок того же `type` (например ещё один блок "новости"
  в другом месте страницы).

Фронтенд на Next.js получает `GET /api/site/home` и рендерит секции по
`type` в порядке `order`, обращаясь к нужному React-компоненту.
